# GH-25 Spark Worker — independent architecture, security and CX critic

## Findings and resolutions

1. **HIGH — old Firebase Functions architecture incompatible with Spark (removed).** Previous GH-25 draft PR #23 used Cloud Functions 2nd gen and Secret Manager in the Firebase project; both required Google Cloud billing. New Worker code lives entirely under `workers/lch-lead-mail` and changes no Firebase plan, database or browser source. The old PR must be closed as superseded, not merged.
2. **HIGH — mail authorization must not be tenant-wide (release-blocking).** Graph `Mail.Send` application permissions granted without scope allow any mailbox. Require Exchange Application RBAC `Application Mail.Send` scoped solely to `contacto@lch-technologies.com`; do not grant a separate, unscoped Entra `Mail.Send` role. Positive and negative sender-authority tests are mandatory before production.
3. **HIGH — secrets and Firestore privilege boundary (mitigated, deployment-blocking).** The Worker needs a server-side Google service account JSON (IAM rather than client Firestore rules), an Entra app and credentials. These belong in Cloudflare Worker secrets with named-database IAM least privilege. No keys may be committed to GitHub or exposed as Vite variables. No secrets are configured today.
4. **HIGH — Firestore optimistic lock response (fixed).** Firestore REST returns HTTP 400 with canonical `FAILED_PRECONDITION` when a CAS `currentDocument.updateTime` fails in some deployments, not only 409/412. Client parses only machine error status and treats the former as a conflict rather than attempting Graph delivery; test added.
5. **HIGH — concurrency/retry delivery (mitigated).** A CAS claim and two-minute lease prevent concurrent duplicate sends; accepted status is persisted only after Graph HTTP 202. A crash between accepted send and Firestore acknowledgement may still result in another message on retry. This is disclosed and traceable with `x-lch-lead-id`.
6. **MEDIUM — Cloudflare Free hard budget (fixed and bounded).** Free account's 10ms CPU and 50 subrequests per invocation cannot support unbounded fan-out. Handler scans no more than 5 pages of 40 recent leads and makes at most 6 **attempts** per invocation. The first version counted successes only and could overrun the quota if permissions produced widespread 403; repaired before release. Sustained lead volume over the 200-document scan horizon risks starving older failed leads; operational monitoring of `capped` and a durable cursor/queue is required before high-volume usage.
7. **MEDIUM — historical test leads / privacy (fixed).** `LCH_NOTIFY_FROM` must be set to an activation timestamp; it is mandatory and cannot be in the future. The Worker uses server-side `createdAt` to limit the scan and validates source and consent. It does not send old QA contacts retroactively or accept arbitrary recipient destinations.
8. **MEDIUM — HTML and logging (mitigated).** User content is length-bounded and HTML-escaped; logs contain machine counters only. Outbound Worker `fetch()` always returns 404; no webhook route, browser tokens or unauthenticated ingestion endpoint.
9. **MEDIUM — Graph API 202 is not inbox receipt (release-blocking).** `notification.state=accepted` means provider acceptance only; commercial delivery must be independently verified in all four real mailboxes with Outlook/Exchange trace.
10. **MEDIUM — reliability and operational dependence (mitigated).** Cron runs outside the on-premise Mac and does not rely on n8n uptime. Failure alerts/monitoring of quota, free-tier CPU, blocked attempts, IAM/secret rotation and sending lease state are still production prerequisites.

## Verdict
**Source quality PASS** provided 26+ tests, local Workerd Cron and Wrangler dry-run bundle all remain green. **Production delivery NOT PASS** until Cloudflare OAuth/API scope, Google SA and Microsoft Entra scoped authorization, Worker secrets, Cloudflare Free deployment and verified four-inbox email receipt are complete.

## Firestore rules source cross-check

The current repository `firestore.rules` explicitly `hasOnly` the 12 existing fields on create and denies browser read/update/delete. That prevents browser clients from smuggling a forged `notification.state=accepted` into new records (provided these exact rules are deployed). Server-side IAM is essential; do not weaken these client rules to accommodate the Worker.
